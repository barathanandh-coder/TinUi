# Phase A.6 Advanced Data-Flow Analysis — Capability Audit

## 1. Current A.5.2 Capabilities
A.5.2 currently handles linear dependency propagation, recursive upstream resolution, N-ary expressions, out-of-order declarations, and deterministic `TypeResult` caching within an `AnalysisContext`. It safely catches cycles and leverages `SemanticWorkspace` for cross-file boundaries. It strictly delegates all mathematical and logical meaning directly to the Type Engine without inventing separate type rules.

## 2. Identified Limitations
- **No Branch Awareness**: A.5.2 assumes a single linear flow of execution. It does not understand `if`/`else` divergence or nested conditions.
- **Single-State Mutation**: The current mutation checker simply verifies reassignment validity against the globally declared type, but cannot trace state values mutating conditionally (e.g., `count = 10` in `if`, `count = 20` in `else`).
- **No Path Sensitivity**: It lacks a scoped environment to represent facts that are valid *only* at specific control-flow locations.

## 3. A.6 Goals
- Allow TinPyUI to reason correctly about data flow when execution paths diverge, merge, mutate state, or become conditional.
- Implement branch-sensitive environments.
- Define strict, deterministic rules for merging branch paths without introducing JavaScript-style implicit coercions.
- Preserve beginner-friendly diagnostics while hiding complex compiler internals.
- Introduce zero modifications to Execution IR, runtime, or `.tin` syntax.

## 4. Control-Flow Requirements
The compiler needs to understand divergent paths:
- `if`/`else` control flow branches.
- Nested conditionals.
- Conditional mutations.
The mechanism must answer "What type/value is guaranteed to exist after this branch merges?"

## 5. Branch Environment Design
A.6 requires introducing a `FlowEnvironment` (or scoped context). 
- **Isolation**: Each branch (`TrueBranch`, `FalseBranch`) receives a cloned or layered instance of its parent's `FlowEnvironment`.
- **Local Mutations**: Mutations within a branch only affect its local scope until the branch merges.
- **Semantic Separation**: `SemanticWorkspace` handles file structural identity; `FlowEnvironment` holds transient, location-specific data-flow facts.

## 6. Branch Merge Rules
When branches merge, the resulting type is determined deterministically by the Type Engine:
- **Same type**: `Int` + `Int` → `Int`.
- **Compatible types**: `Int` + `Float` → `Float` (following explicit Type Engine widening).
- **Incompatible types**: `String` + `Int` → `TypeConflict`.
- **Unknown branches**: `Unknown` + `Int` → `Unknown`.
- **Any branches**: Handled strictly via existing A.5.2 `Any` rules (no implicit bypasses).
If branches yield incompatible types, the compiler will emit a beginner-friendly `TypeMismatch` diagnostic, avoiding "union" type complexities.

## 7. Mutation / Assignment Analysis
Analysis must track the latest-valid definition within the active `FlowEnvironment`:
```tin
state count = 0
if condition:
    count = 10
count = count + 1
```
The analysis environment must record `count` as `Int` natively, evaluate `count + 1` safely, and track multiple reassignments linearly per-path. Assignment compatibility remains strictly governed by `type_engine.go`.

## 8. Loop Analysis
Loops (`for`, `while`) introduce repeated execution and loop-carried state. 
- **Recommendation**: Defer full loop-carried state analysis to A.7 to prevent compounding scope.
- **If Included**: Requires a fixed-point evaluation strategy with strict termination guarantees (iteration limits). If divergence does not settle within N iterations, gracefully fallback to `Unknown` to prevent compiler panics.

## 9. Cross-File Analysis
Branch-sensitive analysis must interact seamlessly with the existing `SemanticWorkspace`.
- Exported components represent their public interface signatures.
- Internal branch state does not leak across `tinpy://` file boundaries unless explicitly passed as a returned parameter or property argument.

## 10. Memoization / Invalidation
A.5.2's `AnalysisContext` caching must be extended.
- **Context-Bound**: Caches must now incorporate the control-flow path or environment ID as part of the key.
- **No Stale Data**: Caches strictly live within the `AnalysisContext`. The AST `DataFlowNode` remains immutable regarding cached paths.
- **Invalidation**: Fully transient caches implicitly prevent stale reuse during live workspace updates.

## 11. Complexity Analysis
Fully path-sensitive analysis risks exponential path explosion ($O(2^N)$).
- **Strategy**: TinPyUI will adopt **Path-Insensitive Branch Merging** (limited sensitivity). Instead of enumerating every path, branches merge back into a single unified `FlowEnvironment` at the end of the `if`/`else` block. 
- This guarantees $O(N)$ linear-time performance per component analysis while maintaining strict correctness.

## 12. Diagnostic / UX Design
Diagnostics must remain beginner-friendly and devoid of jargon.
- **Good**: "Variable 'count' might be a String or an Int depending on the branch."
- **Good**: "Cannot assign a String to 'count' because it requires an Int."
- **Bad**: "ControlFlowNode merged TypeString and TypeInt."

## 13. Architecture Options
- **Option A (Extend Data-Flow Graph)**: Augment `DataFlowAnalyzer` with `FlowEnvironment` stacking during its AST recursive walk.
- **Option B (Separate Control-Flow Graph)**: Build a dedicated CFG structure explicitly mapping basic blocks.
- **Option C**: Pure AST visitor with scoped type environments.

## 14. Recommended Architecture
**Option A / C Hybrid**: Extend the existing `DataFlowAnalyzer` AST visitor to push/pop a `FlowEnvironment` map. This natively avoids building a redundant CFG while successfully tracking scoped branch states, keeping memory usage minimal and preserving current LSP alignment.

## 15. A.6 Scope
- Implement `FlowEnvironment` scope stacking.
- Implement conditional `if`/`else` analysis.
- Implement deterministic branch-merge rules.
- Emit human-readable branch conflict diagnostics.

## 16. Deferred Work
- Full Loop-carried state analysis (deferred to A.7).
- Inter-procedural/cross-component deep branch reasoning (deferred).

## 17. Test Strategy & Visual Validation
- Unit tests for identical branch merging (`Int` + `Int`), widened merging (`Int` + `Float`), and conflicts (`String` + `Int`).
- `Any` and `Unknown` isolation across branches.
- Mutated state persistence post-merge.
- Guarantee $O(N)$ time scaling tests on deeply nested `if`s.

### Real .tin Pipeline Requirements
Every A.6 capability MUST be tested via a small, realistic `.tin` example executing through the entire compiler pipeline. These examples serve as both tests and **Human Review Artifacts** to guarantee syntax naturally fits the developer UX.
- **Directory**: Must be placed in `examples/a6/` (e.g., `basic_if/`, `if_else/`, `nested_branches/`, `branch_merge/`, `branch_conflict/`, `branch_mutation/`, `any/`, `unknown/`, `cross_file/`).
- **Syntax Constraint**: MUST use only existing public TinPyUI syntax. No compiler-centric test syntax may be introduced. If existing syntax cannot naturally express a scenario, it must be reported rather than inventing new syntax.
