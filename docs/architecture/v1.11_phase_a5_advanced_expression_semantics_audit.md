# Phase A.5 — Advanced Expression & Data-Flow Semantics

## 1. Objective and Context
Phase A.4.6 established component-level type safety (detecting missing properties, unknown properties, and type mismatches on component invocations) and introduced cross-file component type resolution.

Phase A.5 expands the semantic analysis deeper into the AST, moving from component boundaries to **inline expressions, data-flow propagation, and branch awareness**. The goal is for the TinPyUI compiler to understand and propagate types across arithmetic expressions, state assignments, and conditionally branched logic, producing human-readable diagnostics while preserving the execution IR.

## 2. Current Capability Audit (Baseline v1.11 pre-A.5)

The current `DataFlowAnalyzer` and `TypeEngine` have rudimentary capabilities introduced in A.4.1/A.4.2:
*   **Expression Typing**: Rudimentary support via `InferExpression()` and `InferLiteral()` (limited to regex matching on basic strings/ints/floats/bools).
*   **State-Dependent Inference**: Very basic. Currently, `state count = 10` is inferred as `TypeInt`, and `count += 1` performs a basic compatibility check (widening).
*   **Data-Flow Propagation**: Currently limited to state initialization and explicit mutations within a component. Does not robustly track multi-hop dependencies (e.g., `state tax = price` -> `state total = tax + 10`).
*   **Branch Awareness**: Non-existent. `if/else` statements are parsed into the AST, but the Type Engine currently ignores branching logic, treating all paths as flat or unresolved.
*   **Diagnostics**: Current `TypeDiagnostic` logic occasionally emits internal TypeKind values (e.g., `"Cannot assign result of TypeString to TypeInt"`). 

## 3. A.5 Design Specifications

### 3.1. Expression Typing Architecture
The Type Engine must accurately infer complex inline expressions without relying purely on string tokenization.
*   `10 + 20` -> `Int`
*   `10 + 2.5` -> `Float` (Implicit widening)
*   `"Hello" + name` -> `String`
*   `age > 18` -> `Bool`
**Implementation Rule**: The `FileAST` will need expanded support for binary expression nodes, or the TypeEngine must leverage a recursive descent expression evaluator that maps `+`, `-`, `*`, `/`, `>`, `<` to their deterministic resultant `TinType`.

### 3.2. Data-Flow Propagation (Multi-Hop)
When state values are derived from other state values, the graph must propagate the type forward dynamically:
```tin
state price = 100         // Inferred: Int
state tax = price         // Propagated: Int
state total = tax + 10.5  // Propagated: Float
```
**Implementation Rule**: Enhance `dataflow_analyzer.go` to traverse `FlowDependency` edges chronologically or topologically to resolve types iteratively.

### 3.3. Branch Awareness
The semantic analyzer must incorporate context constraints introduced by control flow.
```tin
if logged_in:
    // path A
else:
    // path B
```
**Implementation Rule**: Introduce a scoped `TypeEnvironment` (or enhance `SemanticWorkspace` with lexical scope awareness) to ensure variables and state mutations are evaluated within their respective control-flow paths.

### 3.4. Human-Readable Diagnostics
Diagnostics must be cleansed of compiler jargon.
*   **Bad**: `TypeConflict: Cannot assign result of TypeString to TypeInt`
*   **Good**: `TypeMismatch: Cannot add String to Int`
*   **Good**: `TypeMismatch: Cannot assign String to state 'count' (expected Int)`

## 4. Double Evaluation Criteria

For every feature implemented in A.5, the following strict evaluation must be applied:

1.  **Technical Correctness**: Does the Type Engine successfully traverse the AST, correctly apply widening/propagation rules, and emit deterministic structured diagnostics without altering the `app.ir.json`?
2.  **User Experience Check**: Is the resulting diagnostic immediately actionable by a beginner? Does it avoid mentioning "Semantic Graph", "Data-Flow edges", or "Type Inference Trees"?

## 5. Next Steps
Once this design is approved, implementation will proceed systematically starting with **A.5.1: Expression Typing & Propagation**, followed strictly by the Double Evaluation Criteria.
