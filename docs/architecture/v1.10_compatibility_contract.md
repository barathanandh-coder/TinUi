# TinPyUI v1.10 — Compatibility Contract

This document formally defines the backward compatibility guarantees introduced in TinPyUI v1.10, relative to the prior v1.9 baseline. It explicitly separates what constitutes a stable public contract from what remains an unconstrained internal implementation detail.

## 1. Core Compatibility Guarantees (v1.9 → v1.10)

TinPyUI v1.10 is a major architectural evolution bringing AI-driven semantic capabilities. Despite this, it enforces strict backward compatibility guarantees in the following layers:

| Layer | v1.10 Guarantee |
|---|---|
| **`.tin` source** | Existing valid v1.9 source remains strictly valid and parses identically. |
| **Python Bridge** | Existing supported v1.9 Python integration workflows remain supported. |
| **Execution / WASM** | Existing execution semantics, AOT compilation, and target outputs (WASM, Android, iOS, Desktop) preserve exact runtime fidelity. |
| **LSP Operations** | Standard v1.9 LSP lifecycle events (`didOpen`, `didChange`, `didClose`) remain valid; semantic capabilities added in v1.10 are strictly additive. |
| **JSON-RPC Protocol** | Existing v1.9 supported requests and standard responses remain fully compatible where explicitly covered by the machine protocol specification. |

## 2. New v1.10 Capabilities

The following systems are formally introduced in v1.10 and constitute a *new* public contract. They are not bound by v1.9 compatibility, but they establish the baseline for future versions:

- **The `context.*` API**: The public semantic read and mutator endpoints.
- **The Transaction System**: The Propose → Validate → Apply state machine.
- **The Semantic Graph**: The serialized JSON schemas (e.g., `ArchNode`) returned by semantic queries.

## 3. Backward Compatibility ≠ Internal Stability

A stable public API does not imply that the underlying codebase is frozen. The following distinction is absolute:

### ✅ STABLE (Public Contract)
TinPyUI guarantees the stability of these interfaces against breaking changes:
- The JSON-RPC Machine Protocol endpoints and behavior.
- Documented JSON serialization schemas (e.g., the JSON shape of a dependency graph).
- The transaction lifecycle rules (Propose, Apply, Rollback).
- The documented error codes and their specific operational semantics.
- `.tin` language source compatibility.

### ❌ NOT STABLE (Implementation Details)
TinPyUI reserves the right to heavily refactor or replace these at any time without warning:
- The `agent` and `compiler` Go package internal boundaries.
- The Go `SemanticWorkspace` and `SemanticIndex` structures.
- The Go `ArchNode` structs mapping to the serialized schemas.
- Internal VFS vs. Workspace mutex implementations (`docMutex`, `vfsMutex`, `ws.mu`).
- The internal structure of the `AIContext` proposal registry.

## 4. Semantic Protocol Versioning Policy

For all machine-protocol and AI context endpoints, TinPyUI classifies future changes according to the following strict policy:

### Compatible Changes
*These changes do not break the contract and will be shipped in minor updates:*
- Adding new endpoints (e.g., `context.refactor`).
- Adding additive, optional fields to existing JSON request parameters.
- Adding new semantic data fields to existing JSON response payloads.
- Expanding the domain of recognized error codes without altering existing ones.

### Potentially Breaking Changes
*These changes break the contract and require major version bumps (e.g., v2.0):*
- Removing an existing endpoint.
- Making a previously optional JSON field mandatory.
- Changing the type or expected meaning of an existing JSON field.
- Changing the behavioral semantics of the `context.apply` transaction rules (e.g., altering how rollbacks are decided).
- Repurposing existing error codes to mean something different.
