# TinPyUI v1.11 — Phase A.4.5: Component Type Model Design

This document formalizes the internal design and mechanics of introducing Component Property Signatures into the TinPyUI AST and Type Engine. It adheres strictly to the rule of absolute backward compatibility with existing untyped `.tin` components.

---

## 1. AST Representation & Legacy Compatibility

### Typed Properties in the AST
To support type signatures, the AST `Component` struct will transition from `Args []string` to a strongly structured property declaration list.

```go
type PropDecl struct {
	Name     string
	TypeHint string // e.g., "String", "Bool". Empty if untyped.
	Default  string // Raw literal string if a default is provided.
}

type Component struct {
	Name      string
	Props     []PropDecl // Replaces Args []string
	// ... (States, Mutations, RootNodes remain unchanged)
}
```

### Preserving Existing `.tin` Syntax
Legacy untyped properties remain entirely valid.
- `component Button(text, disabled)` parses as:
  - `PropDecl{Name: "text", TypeHint: ""}`
  - `PropDecl{Name: "disabled", TypeHint: ""}`
- The parser will be extended to optionally recognize colons for typing:
  - `component Button(text: String, disabled: Bool)` parses as:
  - `PropDecl{Name: "text", TypeHint: "String"}`

### Untyped Legacy Properties
If a `TypeHint` is empty, the Type Engine explicitly assigns the property a signature of `TypeAny`. This ensures that existing `.tin` components accept any string, number, or dynamic evaluation passed to them, guaranteeing 100% backward compatibility.

## 2. Arguments, Attributes, and Optionality

### Positional vs. Named Arguments
When a component is invoked (e.g., `<Button "Submit" disabled={true} />`), the AST yields `Args []string` and `Attributes map[string]string`. 
The Type Engine will map these to the `Props` signature:
1. **Positional `Args`** map sequentially to the defined `Props` in order.
2. **Named `Attributes`** map strictly by key.

### Optionality & Default Values
Default values are strictly authoritative for both optionality and type inference.

- `disabled: Bool = false`
  - `type     = Bool`
  - `optional = true`
  - `default  = false`
- `disabled: Bool`
  - `type     = Bool`
  - `optional = false`
- `disabled` (Legacy untyped)
  - `type     = Any`
  - `optional = true`

### Inference Precedence
When determining the final signature for a property, the following precedence is strictly evaluated:
1. **Explicit TypeHint** (Always wins; mismatch with default value yields a diagnostic, but hint remains the signature).
2. **Default-value type** (Inferred via Literal Inference).
3. **Any** (Legacy untyped).

A default must **not** silently override an explicitly stated incompatible type.

---

## 3. Type Checking Mechanics

### `{dynamic}` Values
Dynamic curly-brace interpolation (e.g., `<Button disabled={loading} />`) is already inferred by the Type Engine (A.4.2) as `TypeAny`.
Assigning `TypeAny` to a strictly typed property (`disabled: Bool`) evaluates as a *valid assignment*, short-circuiting validation. This allows dynamic execution to seamlessly pass through the static analyzer.

### Any and Unknown Handling
- `Any` satisfies all property types (as seen with dynamic values and untyped props).
- `Unknown` satisfies all property types defensively to avoid cascading false-positive diagnostics when a preceding inference fails.

### Missing, Unknown, and Duplicate Properties
- **Missing Required Property**: Generates a `MissingProperty` diagnostic.
- **Unknown Property Supplied**: Passing `unknownProp="123"` generates an `UnknownProperty` diagnostic (but does not fail compilation).
- **Duplicate Properties**: E.g., `<Button text="A" text="B" />`. Evaluates the final property (overwrites) and generates a `DuplicateProperty` diagnostic.

## 4. Component Types & Cross-File Resolution

### Component Type Representation
When an invocation is processed, the Type Engine generates a `TypeResult` representing the component instance.
```go
TinType{
    Kind: TypeComponent,
    ComponentID: "tinpy://ui/button.tin#Button", 
}
```
The `ComponentID` is a fully qualified URI referencing the Semantic Graph ID.

### Imported Component Signatures
To validate properties of an imported component:
1. The Type Analyzer asks the Semantic Graph to resolve the `RelImports` boundary.
2. It fetches the `ComponentID` of the target.
3. It recursively requests the `PropDecl` signature of the target component from the Type Analyzer's context.
4. If the target file is unavailable or unresolved, the signature evaluates to `TypeUnknown`, and all passed properties are accepted defensively.

### Recursive / Self-Referencing Components
If `<Tree>` renders `<Tree>`, the Type Engine uses its existing cycle detection logic (from Phase A.4.3). Since we only fetch the *signature* (the `PropDecl` list) and do not traverse the target's render tree, property validation on recursive components resolves cleanly in `O(1)` without stack overflows.
