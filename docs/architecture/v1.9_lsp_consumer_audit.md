# v1.9 Phase 3: LSP Consumer Audit

**Status:** COMPLETE (Read-Only Audit)
**Target:** TinPyUI v1.9 / VS Code Integration

## 1. Executive Summary
The central question: *"Can a strict LSP consumer drive useful IDE intelligence using the existing machine protocol alone?"*

**Answer: NO.**
While the existing v1.9 Machine Protocol provides an excellent foundation for CI/CD and batch analysis, it lacks the stateful document synchronization, in-memory buffer analysis, and semantic querying endpoints required to power a Language Server Protocol (LSP) consumer efficiently. 

An LSP adapter built today would be restricted to "on-save" diagnostic polling, similar to a basic linter, rather than providing rich IDE intelligence.

## 3. Protocol Deficiencies

### A. Document Synchronization (In-Memory Buffers)
**Issue:** The `check` and `build` commands currently accept a file path (`{"entry": "file.tin"}`) and read directly from the disk. 
**Impact:** LSP servers receive code changes on every keystroke via `textDocument/didChange`. If the protocol cannot accept a raw text buffer, the IDE must save to a temporary file before invoking `check`, which introduces severe latency and disk wear.
**Verdict:** JUSTIFIED protocol requirement.

### B. One-Shot Performance Overhead
**Issue:** The current normative mode is one-shot execution.
**Impact:** Spawning a new Go process (`tinui agent check`) for every keystroke validation is too slow for 16ms IDE responsiveness constraints.
**Verdict:** JUSTIFIED protocol requirement. The `daemon` mode must be implemented to maintain persistent AST memory.

### C. Semantic Querying (Hover, Completion, Definition)
**Issue:** The protocol only exposes structural commands (`build`, `check`, `graph`). It does not expose semantic AST lookups based on cursor position.
**Impact:** Impossible to implement jump-to-definition, type-aware autocompletion, or documentation hover.
**Verdict:** JUSTIFIED protocol requirement.

---

## 4. Proposed Protocol Amendments (Phase 3)

To unblock the LSP adapter, the following extensions to the Machine Protocol are required:

1. **VFS (Virtual File System) Support**:
   Commands like `check` must optionally accept `{"sourceText": "..."}` or there must be `updateBuffer` commands to sync memory state before calling `check`.
2. **Daemon Mode Execution**:
   A persistent JSON-RPC session where the AST remains in RAM across requests.
3. **Semantic Query Endpoints**:
   *   `agent query_hover` (Given line/character, return documentation)
   *   `agent query_definition` (Given line/character, return file/line/character)
   *   `agent query_completions` (Given line/character, return suggestion list)

## 5. LSP Adapter Architecture

Given the protocol, the intended VS Code extension architecture should be:

```text
[VS Code Client] (TypeScript)
       │
       │ (Standard LSP over IPC)
       ▼
[LSP Middleware Server] (TypeScript)
       │
       │ (Spawns `tinui agent --daemon`)
       │ (JSON-RPC Machine Protocol over stdin/stdout)
       ▼
[TinPyUI Go Agent Daemon]
```

**Why a TypeScript Middleware?**
The Go agent handles AST parsing, validation, and semantic logic. The TS middleware purely translates standard LSP requests (like `textDocument/completion`) into TinPyUI Machine Protocol requests (`query_completions`), shielding the Go compiler from strict LSP structural dependencies.

---

## 6. Recommended Implementation Sequence

1. **Protocol Amendment**: Add `updateBuffer` (or `sourceText` injection) to the schema to support unsaved files.
2. **Protocol Amendment**: Implement `tinui agent --daemon` in Go to maintain a persistent JSON-RPC loop.
3. **Protocol Amendment**: Introduce semantic endpoints (`query_hover`, `query_completions`).
4. **Tooling**: Scaffold the VS Code extension (`vscode-tinpyui`) containing the TS Middleware.
5. **Integration**: Wire the TS Middleware to the Go `--daemon` agent.
