# TinPyUI v1.11 — Phase A.2: Type Model Design

This document formalizes the internal design and mechanics of the standalone Type Engine for TinPyUI. This semantic overlay adheres strictly to the boundary constraint: it may enrich semantic understanding but must never mutate the canonical AST, Semantic Graph, or execution IR.

---

## 1. Type Universe

The type system is modeled as a deterministic enumeration of specific base constructs:

- `String`: Represents textual data (e.g., `"hello"`, f-strings).
- `Int`: Represents whole numeric data (e.g., `42`).
- `Float`: Represents fractional numeric data (e.g., `42.5`).
- `Bool`: Represents logical truth (e.g., `true`, `false`).
- `Null`: Represents explicit absence of value (e.g., `null`).
- `Unknown`: An *Uncertainty Marker*. Signifies that the static engine cannot determine the type (e.g., complex unresolvable expression). Validation systems must treat `Unknown` carefully to prevent false positive errors.
- `Any`: A *Top Type*. Explicitly allows assignability to/from all types (used heavily for dynamic Python boundary inputs).
- `Component`: Represents an instantiated UI component (e.g., `<Button>`). Includes metadata tracking its specific component ID.
- `Collection`: Parameterized types representing arrays or dictionaries (e.g., `List<String>`).

---

## 2. Type Representation & Identity

Types are represented not as raw strings but as structured Go types within the Engine:

```go
type TypeKind string

const (
	TypeString    TypeKind = "String"
	TypeInt       TypeKind = "Int"
	TypeFloat     TypeKind = "Float"
	TypeBool      TypeKind = "Bool"
	TypeNull      TypeKind = "Null"
	TypeUnknown   TypeKind = "Unknown"
	TypeAny       TypeKind = "Any"
	TypeComponent TypeKind = "Component"
	TypeCollection TypeKind = "Collection"
)

// TinType represents the resolved identity of a type
type TinType struct {
	Kind         TypeKind
	ComponentID  string     // Populated only if Kind == TypeComponent
	ElementType  *TinType   // Populated only if Kind == TypeCollection
}
```

---

## 3. Inference Confidence & Provenance

To allow consumers (LSP/AI) to weigh the validity of an inferred type, the engine encapsulates the resolved `TinType` in a `TypeResult`.

```go
type ConfidenceLevel int

const (
	ConfidenceExplicit ConfidenceLevel = iota // Type hint or API schema
	ConfidenceLiteral                         // Directly parsed literal ("hello")
	ConfidenceInferred                        // Propagated from operators (+)
	ConfidenceUnknown                         // Failed resolution
)

type TypeResult struct {
	Type       TinType
	Confidence ConfidenceLevel
	SourceID   string       // The AST Node ID / Range that dictated this type
}
```

### Inference Precedence
When resolving conflicts or aggregating types, precedence dictates victory:
1. `Explicit` (Always wins)
2. `Literal` (Wins over inferred operations)
3. `Inferred` (Contextual deduction)

---

## 4. Assignability Rules

Type assignment is validated strictly based on origin (`FromType`) and destination (`ToType`).

- **Identity**: `A` is assignable to `A`.
- **Any**: `Any` is assignable to all types. All types are assignable to `Any`.
- **Unknown**: All types are assignable to `Unknown` (silent pass). Assigning `Unknown` to an explicitly typed variable yields a low-confidence assignment, but typically does not throw a hard error unless strict mode is enabled.
- **Null Compatibility**: By default, TinPyUI types are nullable. `Null` is assignable to `String`, `Int`, `Float`, `Bool`, `Component`, and `Collection`.
- **Widening/Narrowing**: `Int` is assignable to `Float` (widening). `Float` is not assignable to `Int` (narrowing).

---

## 5. Conflict Handling & `TypeConflict`

A conflict occurs when a deterministic assignment severely violates the assignability rules (e.g., `FromType = String`, `ToType = Int`, Confidence: `Literal`).

Rather than mutating the semantic graph or throwing a panic, the Type Engine generates a **Deterministic Conflict Diagnostic**. 

- The resulting expression yields `Unknown`.
- The Type Engine stores a diagnostic marker internally (`TypeDiagnostic{Range, Message, Severity}`).
- The AI / LSP queries `context.diagnostics` or `context.types` and sees the `TypeConflict` explicitly surfaced.

*Crucially: Execution continues. The Type Engine warns; it does not block compilation.*

---

## 6. Unknown Propagation

Operations involving `Unknown` defensively propagate `Unknown`.
- `Int + Unknown` → `Unknown`
- `<Component prop={Unknown}>` → Prop type requirement ignored (no diagnostic emitted to prevent false positives).

---

## 7. Cross-File Type References

TinPyUI is multi-file. A component `<Button>` imported from `button.tin` may dictate property expectations.

- The Type Engine leverages the existing Semantic Graph (`RelImports` edges) to resolve types across boundaries.
- If `TargetID` for an import is `IsUnresolved`, the Type Engine yields `Unknown` for any property validations against that component.
- The VFS locking order (`vfsMutex` -> `docMutex`) currently guaranteeing safe multi-file references strictly applies to the Type Engine resolution. No cyclical deadlocks are permitted.
