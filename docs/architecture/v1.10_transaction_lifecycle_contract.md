# TinPyUI v1.10 — Transaction Lifecycle Contract

This document formally defines the externally observable transaction behavior for TinPyUI's AI-controlled development layer. It establishes the strict rules governing how an external agent's proposed changes are validated, approved, and committed to the semantic workspace.

## 1. The Transaction State Machine

The entire lifecycle follows an explicitly guarded state machine:

```text
PROPOSE
   ↓
VALIDATE
   ↓
APPROVAL BOUNDARY
   ↓
APPLY
   ↓
COMMIT
   └── or ──→ ROLLBACK
```

**Core Principle:**
> **`context.propose` validates a candidate change. `context.apply` commits an already validated proposal under TinPyUI's transaction rules.**

## 2. Phase: Propose & Validate

### Proposal Creation
When an external agent issues a `context.propose` request, TinPyUI constructs a temporary sandbox. The candidate source is parsed to ensure syntactical correctness and local semantic validity.

### Deterministic `ProposalID`
If the validation succeeds, the backend generates a deterministic `ProposalID` representing the exact patch for the targeted file at a specific version. This ID is stored in the internal proposal registry.

### `expected_version` Requirement
Every proposal is strictly bound to an `expected_version`. This integer must match the active Virtual File System (VFS) version (incremented via LSP `textDocument/didChange` events). Proposals submitted against stale versions are instantly rejected.

## 3. Phase: The Approval Boundary

Once a `ProposalID` is issued, the transaction enters the **Approval Boundary**.
- TinPyUI does **not** commit proposals automatically.
- The external AI agent is expected to pause and present the `ProposalID` to the human developer or IDE host system.
- The proposal remains dormant in the registry until either consumed or invalidated by a VFS update.

## 4. Phase: Apply & Commit/Rollback

The execution of a `ProposalID` occurs exclusively via the `context.apply` endpoint.

### Preconditions
`context.apply` enforces the following preconditions before acquiring commit locks:
1. The `ProposalID` must exist and must not have been previously consumed.
2. The targeted URI must be open in the workspace.
3. The `expected_version` supplied during the `apply` call must perfectly match the active VFS version.

### Atomic VFS + Semantic Workspace Update
Once preconditions are met, the transaction locks the specific URI's synchronization lane. The VFS is updated, followed immediately by the `SemanticWorkspace`.

### Semantic Regression Detection
TinPyUI performs a global "pre vs. post" comparison across the entire workspace.
- **Pre-Apply:** The total number of unresolved semantic references is calculated.
- **Post-Apply:** The total number of unresolved semantic references is recalculated.

If the post-apply state contains *more* unresolved references than the pre-apply state (e.g., the proposal renamed an exported component, breaking dependents in 3 other files), TinPyUI flags a **Semantic Regression**.

### Full Rollback Semantics
If a semantic regression is detected, the transaction is completely rolled back atomically:
1. The VFS is restored to the previous source.
2. The `SemanticWorkspace` re-parses the previous source.
3. The original state is perfectly recovered.

### `Applied: false` vs. JSON-RPC Errors

> **A semantic rollback is not a JSON-RPC request failure. The request executes successfully and returns `Applied: false` with the rollback outcome.**

- **JSON-RPC Error (e.g., `-32003 Version Mismatch`)**: The request itself failed before the transaction began. The transaction was never attempted.
- **`Applied: false`**: The transaction executed, the backend observed destructive semantic behavior, and safely performed an atomic rollback. The JSON-RPC request itself succeeded in its duty.

### Proposal Replay Prevention
A `ProposalID` is strictly single-use. Once `context.apply` executes (regardless of a Commit or Rollback outcome), the `ProposalID` is instantly deleted from the registry. External agents cannot brute-force or replay a consumed proposal.

## 5. Concurrency & Invariants

The Machine Protocol guarantees robust handling of concurrent requests.

### Concurrency Guarantees
- Simultaneous `context.apply` requests targeting the same URI are correctly serialized.
- An incoming `textDocument/didChange` LSP event concurrent with a `context.apply` will safely resolve according to lock acquisition. The slower operation will safely fail due to a version mismatch constraint.

### Post-Transaction Invariants
After any transaction (Commit, Rollback, or Rejection), the following architectural rule remains absolute:

```text
For every synchronized URI:
VFS version >= Semantic Workspace version
```

### What an External AI Agent Can and Cannot Assume
- **Can assume**: If `Applied: true` is returned, the change has been universally synchronized, and all subsequent `context.*` read queries will instantly reflect the new AST.
- **Can assume**: If `Applied: false` is returned, absolutely zero side-effects occurred in the workspace.
- **Cannot assume**: The agent cannot assume a proposal will remain valid indefinitely. Human typing will advance the VFS version, implicitly invalidating outstanding proposals.
