# v1.10 Semantic Graph Schema Design

This document details the architectural design for the v1.10 Semantic Graph, outlining how the extended AST is mapped into an AI-agnostic intelligence layer. The JSON Schema defining the exact structural types is provided alongside this document in `v1.10_semantic_graph_schema.json`.

## Architecture Layers

```text
                 ┌→ Semantic Graph → LSP / Agents / Tools
AST ─────────────┤
                 └→ Execution IR → Runtime
```

The Semantic Graph sits above the execution IR, entirely decoupled from WebAssembly optimizations, retaining relationships, boundaries, and exact source code locations.

## Schema Core Answers

### 1. What is a symbol?
A symbol is a strongly-typed named entity possessing a distinct declaration range and lifecycle. In TinPyUI, symbols map to: `Component`, `State`, `Definition` (mutations), and `Event`. 

### 2. What constitutes a reference?
A reference is a `Relationship` object associating a source symbol to a `target_id`. Supported relationship kinds:
- `reads`: A component or mutation accessing a `State`.
- `triggers`: A UI node or event firing a `Definition`.
- `renders`: A component instantiating a child `Component`.
- `imports`: A file declaring a dependency on an external symbol.

### 3. How are components uniquely identified?
Symbols are identified via a stable, deterministic URI format:
`tinpy://<workspace-root>/<relative-file-path>#<qualified-name>`
*(e.g., `tinpy:///project/src/ui.tin#Card`)*. This ensures a component ID remains stable across file edits.

### 4. How are cross-file imports represented?
Using the `imports` relationship type attached to a `File`. These point directly to the deterministic `SymbolID` of the target being imported.

### 5. How are unresolved references represented?
If an import or component instantiation points to a `SymbolID` that does not exist in the Project index, the `target_id` is retained, but the referencing graph marks it internally, or the symbol is flagged with `is_unresolved: true`. This prevents the graph from breaking on typos.

### 6. How are types represented?
Types are primarily categorized by `SymbolKind`. Extended type validation (e.g. `number` vs `string` on State) can be stored within a symbol's metadata, but for v1.10, structural kinds drive the LSP logic.

### 7. How are source ranges represented?
Ranges strictly adhere to the LSP specification using zero-based, UTF-16 indexed positions.
```json
"range": {
  "uri": "file:///...",
  "start": { "line": 0, "character": 0 },
  "end": { "line": 0, "character": 12 }
}
```

### 8. How are parent/child relationships represented?
Through a dual mechanism: 
1. Semantic back-pointers: `parent_id` points to the enclosing scope (e.g. a State's parent is its Component).
2. The hierarchical JSON structure of the `Project -> File -> Symbol` tree.

### 9. How are dependencies represented?
As directed edges. Every `Symbol` maintains a `relationships` array. To query what a component depends on, iterate its `relationships`. To query what depends on a component, the Project layer maintains an inverted index.

### 10. Which graph data is persisted versus derived?
- **Persisted (File-level)**: Explicit symbols, local relationships, and AST ranges.
- **Derived (Project-level)**: The inverted reference index (who imports what) and global resolution tracking.

### 11. How does the graph change when a file changes?
When a `.tin` file updates, only that specific `File` object is purged and rebuilt from the new AST. The Project layer then recalculates the inverted index. The rest of the graph remains untouched.

### 12. Can the graph support rename/references without parsing the entire project?
Yes. Because IDs are deterministic, renaming `Card` to `HeroCard` simply requires finding all files in the inverted index referencing `tinpy://...#Card` and updating their ranges. However, building the initial inverted index requires a one-time project-wide parsing.

### 13. What information is deliberately NOT included?
- Raw HTML tags (`div`, `span`) unless they bind state or events.
- Comments, whitespace, and formatting.
- Execution semantics (e.g., memory bounds, rendering loops, and WebAssembly instruction opcodes). The Semantic Graph models the project, not the runtime.
