# TinPyUI v1.11 — Phase A.4.6.4: Cross-File Component Signature Resolution Design

This document details the precise design for bridging Component Type Checking across file boundaries, adhering strictly to the architecture constraints set in A.4.6.3.

## 1. Preserving Component Signatures in the Semantic Graph
Currently, when an AST `Component` is analyzed, its signature is discarded.
- **Change:** We will extend the `Symbol` struct in `semantic_analyzer.go` to securely house the signature:
  ```go
  type Symbol struct {
      // existing fields...
      Props []PropDecl `json:"props,omitempty"`
  }
  ```
- **Constraint:** This requires zero changes to the Execution IR or the v1.8 runtime. The semantic graph purely becomes more descriptive.

## 2. Resolving Cross-File Signatures
The `ComponentTypeChecker` will be upgraded from a purely local validator to a workspace-aware analyzer.

**Signature Update:**
```go
func (c *ComponentTypeChecker) CheckWorkspace(ast *FileAST, workspace *SemanticWorkspace) []ComponentDiagnostic
```

**Resolution Flow:**
1. During AST traversal, when the checker hits a component invocation (e.g., `<Button>`), it asks the Semantic Graph for the `RelRenders` target ID.
2. It calls `workspace.ResolveSymbol(targetID)`.
3. If the symbol exists, it extracts `Symbol.Props` and executes the exact same validation logic we built in Phase A.4.6.2.

## 3. Defensive Unresolved Handling
If `workspace.ResolveSymbol(targetID)` returns `nil` or a symbol where `IsUnresolved == true`:
- The component's expected signature is classified as `Unknown`.
- **Constraint:** The Type Checker must *provisionally accept* all passed properties without emitting `UnknownProperty`, `TypeConflict`, or `MissingProperty` errors.
- **Diagnostic:** It will yield exactly one error: `UnresolvedComponentReference`. This inherently prevents cascading downstream noise.

## 4. Deterministic Cycle Protection
If `A.tin` imports `B.tin` and they recursively reference each other's components, we must ensure type checking does not hang.
- **Design:** The `ComponentTypeChecker` will internally manage a `visiting map[string]bool` tracking the `tinpy://` IDs currently under resolution.
- If it encounters a `targetID` already marked as `visiting`, it gracefully breaks the cycle, yields `Unknown`, and suppresses property diagnostics for that branch.

## 5. Duplicate Identity Safety
- Duplicate components defined *within the same file* are naturally rejected by the parser/semantic analyzer.
- Duplicate components defined *across different files* are inherently disambiguated because the target ID embeds the absolute workspace URI (e.g., `tinpy://src/a.tin#Button` vs `tinpy://src/b.tin#Button`).
- The type checker does not silently choose; it strictly follows the deterministic `importMap` generated in `semantic_analyzer.go`.

## 6. Stateless Concurrency
- The checker operates entirely statelessly.
- It leverages the existing `RLock()` bound to `workspace.ResolveSymbol()`.
- If an imported file is modified on disk, the `SemanticWorkspace` seamlessly handles the update via `RemoveFile` and `AddFileAST`. The IDE then commands the checker to re-run, immediately surfacing the freshest signature across the workspace without introducing stale caches or lock inversions.

## 7. Zero Syntax Changes
**Constraint Validation:** This phase introduces strictly zero modifications to `.tin` syntax.
- Beginners write standard components and import statements identically to v1.8.
- The intelligence happens entirely behind the scenes via `tinpy://` URI mapping.
- Legacy components imported across files effortlessly resolve to `TypeAny`.
