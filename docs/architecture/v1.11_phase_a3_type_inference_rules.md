# TinPyUI v1.11 — Phase A.3: Type Inference Rules

This document formally specifies exactly how the standalone Type Engine derives types from the existing raw `.tin` AST. It dictates precedence, resolution boundaries, and deterministic conflict rules without introducing dynamic execution.

> **INVARIANT GUARANTEE**
> Semantic Graph = Structural truth
> Type Engine = Derived semantic analysis
> Execution IR = Runtime truth
> **The Type Engine must never become authoritative over the execution compiler during v1.11.**

---

## 1. Literal Inference
When a raw string from the AST is evaluated in isolation, it is resolved against deterministic literal patterns. Confidence is always `Literal`.

- `\"hello\"` or `'hello'` → `String`
- `42`, `-10` → `Int`
- `3.14`, `-0.5` → `Float`
- `true`, `false` → `Bool`
- `null` → `Null`

## 2. State Operations

### State Initialization
When a `StateDecl` is evaluated, the `Initial` value string is passed through Literal Inference.
- `state count = 10` → `Int` (Confidence: `Literal`)
- `state message = "hello"` → `String` (Confidence: `Literal`)

### State Reassignment & Mutation
When a state is re-evaluated due to a `MutationNode` or an explicit assignment in a `DefNode`, the type engine compares the resulting expression against the initialization type.

- **Valid Widening**:
  - `state price = 10` → `Int`
  - `price = 12.5` → `Float` (Reassignment Literal Inference)
  - Result: `price` is effectively typed as `Float` post-mutation.
- **Type Conflict**:
  - `state count = 10` → `Int`
  - `count = "hello"` → `String`
  - Result: `count` evaluation yields `TypeConflict` (`Int → String`).
- **Mutation Operators (`+=`, `-=`, `*=`, `/=`)**:
  - Strongly infers Numeric bounds (`Int` or `Float`).
  - E.g., `count += 1` confirms `count` must be Numeric. If `count` was previously inferred as `String`, a `TypeConflict` is generated.

## 3. Component Arguments & Attributes
- **Attributes (`<Button title="Click">`)**: Inferred contextually. If the `<Button>` component is defined and its parameter signature is known, the argument is checked against it. If undefined, it resolves to `Unknown`.
- **Component Variables (`<Text>{message}</Text>`)**: Inherits the type of the variable `message` strictly.

## 4. Definitions, Parameters, and Returns
Since the current AST `DefNode` lacks explicit parameters and return values:
- **Parameters**: `Unknown` by default unless explicitly documented in a type hint (to be added in AST). If an event handler passes implicit event data (e.g., `on_click`), it types as `Any`.
- **Return Values**: Computed recursively by evaluating all return pathways in the `DefNode`. If branches diverge (`Int` and `String`), it yields `Unknown` (or a `Union` if supported).

## 5. Expressions & Operators
Expressions are resolved bottom-up.
- `A + B`: 
  - If both `Int` → `Int`
  - If both `Float` → `Float`
  - If `String + String` → `String`
  - If `String + Int` → `String` (via coercion semantics)
- `A > B`, `A == B`, `A && B` → `Bool`

## 6. Collections
If array or dictionary syntax is identified:
- `[1, 2, 3]` → `Collection(Int)`
- `["a", 2]` → `Collection(Unknown)` (mixed types degrade if unsupported).

## 7. Cross-File References
When a symbol refers to an imported component or function:
- The engine uses the `RelImports` edge in the Semantic Graph to fetch the target symbol.
- It recursively asks the Type Engine for the target's type.
- If the import edge is `IsUnresolved`, the target yields `Unknown`.

## 8. Unknown & Any Behavior
- `Any` explicitly short-circuits validation. Assigning an `Int` to an `Any` parameter succeeds without a diagnostic.
- `Unknown` signals inference failure. Assigning an `Unknown` to an `Int` state succeeds, but carries `ConfidenceUnknown`. It acts defensively to prevent the analysis engine from spamming false positives.

## 9. Resolution Precedence & Conflicting Assignments
When multiple inference sources disagree on a single symbol, or during resolution, the Type Engine strictly enforces the following precedence order to prevent non-deterministic results:
1. **Explicit type information** (Directly typed)
2. **Concrete literal information** (Statically verifiable values)
3. **Assignment/data-flow inference** (What it was assigned)
4. **Expression inference** (Contextual usage)
5. **Cross-file symbol inference** (Imported typing)
6. **Any** (Permits any type, does *not* override concrete types)
7. **Unknown** (Fallback)

**Conflict Handling**:
When two concrete incompatible types meet (e.g., `String + Int`), the engine does *not* silently coerce or select one. Instead:
- It yields `Unknown` or `TypeConflict`.
- It generates a diagnostic marker.
- Execution is completely unaffected.

**Any vs Unknown**:
`Any` does *not* automatically override a concrete type. `Any` means "this boundary permits any type", not "we don't know the type."

## 10. Chained & Cyclic Dependencies
- **Chained**: `state a = 10`, `state b = a`, `state c = b`. The engine lazily evaluates `c`, tracing the graph back to `a` (`Int`).
- **Cyclic**: If `a` references `b`, and `b` references `a` (or via recursive components), the Type Engine tracks visit state (`visiting`). If a cycle is detected, it instantly breaks the loop and yields `Unknown` to prevent a stack overflow and keep OODA loops fast.
