# TinPyUI v1.11 — Phase A.1: Type Capability Audit

This document serves as a read-only analysis of the existing TinPyUI compiler architecture (AST, Semantic Graph, and execution semantics). Its purpose is to explicitly map out what type-related information currently exists, what is missing, and where inference opportunities lie, before any implementation of the Type System Model (Phase A.2+) begins.

---

## 1. Abstract Syntax Tree (AST) Capabilities

An audit of `src/compiler/ast.go` reveals that the current AST treats almost all data as raw strings. There are no explicit type fields anywhere in the AST structures.

### Current Data Fields
- **Literals & State Declarations**: 
  - `StateDecl` contains `Initial string`. No explicit type annotations exist.
- **Assignments & Mutations**: 
  - `MutationNode` contains `Operator string` and `Value string`.
- **Component Properties (Arguments/Attributes)**: 
  - `Component` contains `Args []string`.
  - UI `Node` contains `Args []string` and `Attributes map[string]string`. 
  - `IsFString bool` is tracked (implicitly hinting at a string interpolation type).
- **Functions (Definitions)**: 
  - `DefNode` tracks `FuncName` and `Mutations`. It currently lacks input parameters or return values entirely in the AST struct.
- **Expressions**: 
  - `ConditionalNode` tracks `ConditionVar`, `Operator`, and `Value` as raw strings.

**Conclusion**: The AST is currently structurally sound but semantically untyped. All literals, expressions, and properties are raw strings awaiting semantic resolution.

---

## 2. Semantic Graph Capabilities

An audit of `src/compiler/semantic_analyzer.go` and `src/compiler/semantic_index.go` reveals the current limits of the global semantic engine.

### Current Fields
- **Symbol Struct**: Tracks `ID`, `Kind` (`Component`, `State`, `Definition`, `Event`), `Name`, `Range`, `ParentID`, and `Relationships`. 
- **Relationship Struct**: Tracks `Kind` (`renders`, `reads`, `triggers`, `imports`), `TargetID`, and `Range`.

### Type Information Gap
- **Absent**: There is **zero** type information present in the Semantic Graph. 
- `Symbol` has no `Type` or `Signature` field.
- `Relationship` does not track parameter passing or attribute flow types.

**Conclusion**: The semantic graph currently answers "What exists and how things relate" flawlessly, but cannot answer "What things mean".

---

## 3. Existing Language Semantics

Based on the `.tin` parser and Python execution layers, the framework practically supports the following underlying data types, even though the AST doesn't strictly categorize them yet:
- `String`: Handled natively, including f-strings (`IsFString`).
- `Int` / `Float`: Used in mutations (e.g., `count += 1`) and conditionals (e.g., `count > 5`).
- `Bool`: Implicit in conditionals.
- `Null`: Assumed fallback for uninitialized component attributes.
- **Collections**: Arrays/Dictionaries are heavily used in the Python backend (and `ForNode.IterableKey` implies iterables exist).
- **Component / Reference Values**: Implicit when a tag name (e.g., `<Button>`) is invoked.
- **Dynamic Values**: Expressions mapped to `{var}` interpolation.

---

## 4. Inference Opportunities

Because the AST captures exact raw strings for operators and values, the Type Engine has high-confidence inference pathways:

1. **Literal → Type**: 
   - `state name = "Alice"` (regex/parser identifies quotes) → `String`
   - `state count = 10` (numeric regex) → `Int`
2. **State → Type**: 
   - A state symbol inherits the type of its `Initial` literal inference.
3. **Assignment → Type**: 
   - `count += 1` (`+=` operator combined with numeric `1`) strongly infers numeric intent for `count`.
4. **Expression → Type**: 
   - `ConditionalNode` with operator `>` implies both operands are Numeric.
5. **Component Property → Expected Type**: 
   - If a component does `value = {count}`, the property `value` inherently assumes the type of the `count` state.

---

## 5. Conflict Cases

Before implementing the inference rules, we must explicitly define how the Type Engine will handle conflicts that the current string-based parser blindly permits:

- **Mutation Type Conflict**: 
  - `state count = 10`
  - `def click { count = "hello" }`
  - *Current Behavior*: Valid AST, crashes or coerced at execution time.
  - *Required New Behavior*: Type Engine must mark `count` assignment as a `TypeConflict`.
- **Property Type Conflict**:
  - `ComponentA` infers its arg `title` is a `String`.
  - A parent renders `<ComponentA title={10} />`.
  - *Current Behavior*: Valid AST.
  - *Required New Behavior*: Type Engine must mark the `renders` relationship boundary with a diagnostic.
- **Ambiguous Operators**:
  - `+` can mean String Concatenation or Numeric Addition. The inference engine will need fallback rules (`Any` or `Unknown`) if both operands are untyped variables.

---

## Final Status
The audit confirms that the foundation is clean. We do not have to rip out any broken type systems—we are building on a blank slate. The Semantic Graph (`Symbol`) and AST (`Node`, `StateDecl`, `MutationNode`) are perfectly positioned to act as the structural inputs for the new decoupled Type Engine.
