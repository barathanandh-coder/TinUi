# TinPyUI v1.11 — Phase A.4.6.3: Cross-File Component Signature Audit

This document audits the feasibility and behavior of safely extending component property type checking across file boundaries using the existing Semantic Graph architecture.

### 1. How `RelImports` identifies imported files
When a `.tin` file imports another, `semantic_analyzer.go` registers a `RelImports` edge on the `File.Imports` array. The target of this edge is built dynamically via `buildImportID`, translating the path into a universal `tinpy://` URI.

### 2. How `RelRenders` identifies the target component
Invocations capture a `RelRenders` edge. To resolve the target, the analyzer checks an internal `importMap`. If the component name was imported, it uses the mapped `tinpy://` ID. Otherwise, it defaults to a local symbol ID inside the current file.

### 3. Whether the target Component/PropDecl can be retrieved deterministically
**Currently, No.** The `SemanticWorkspace.ResolveSymbol(id)` function successfully retrieves a `*Symbol` representing the target component across files. However, the `Symbol` struct (in `semantic_analyzer.go`) does *not* contain a `Props` field. The component property signature is lost during AST-to-Graph conversion. We will need to append `Props []PropDecl` directly into the `Symbol` definition before cross-file checking is physically possible.

### 4. How `tinpy://` IDs map across files
The `SemanticWorkspace` handles this flawlessly. Because `buildSymbolID` prepends the normalized file URI into the symbol string (e.g., `tinpy://path/to/ui.tin#Button`), components are universally uniquely identified regardless of file borders.

### 5. What happens with unresolved imports
The `SemanticWorkspace` tracks unresolved edges via `IsUnresolved=true`. When the Component Type Checker encounters an unresolved imported component, it must immediately suppress downstream evaluation by defaulting the component signature to `TypeUnknown`. This explicitly guarantees that an unresolved dependency will *not* trigger cascading false-positive property errors.

### 6. Circular imports / Component references
If `A.tin` imports `B.tin` which imports `A.tin`, or if components render each other recursively, we face potential infinite recursion when resolving signatures. We must implement deterministic cycle-detection boundaries (tracking `visited` vs `visiting` IDs exactly as we did in the Data-Flow Analyzer) to short-circuit cycles into `TypeUnknown`.

### 7. Duplicate component names across files
Since the `tinpy://` ID embeds the exact source file path, naming collisions do not occur in the graph (e.g., `tinpy://card1.tin#Button` is distinct from `tinpy://card2.tin#Button`). 

### 8. Legacy untyped components imported from another file
Because `ast.go` and `parser.go` explicitly parse legacy components into `PropDecl` with empty `TypeHint`s, importing a legacy component from another file will automatically present as `TypeAny` globally. Backward compatibility is mathematically guaranteed.

### 9. Version/update behavior when the imported file changes
The `SemanticWorkspace` exposes thread-safe `RemoveFile` and `AddFileAST` functions. When an imported file is modified on disk, the IDE simply swaps out the AST. The next time the Type Checker runs, it effortlessly queries the newly updated `Symbol` signature.

### 10. Can `SemanticWorkspace` locking be reused without lock inversion?
**Yes.** The `SemanticWorkspace.ResolveSymbol` exposes a fast `RLock()`. As long as the Component Type Checker operates purely statelessly as a consumer (read-only analyzer) and avoids holding any internal locks across `ResolveSymbol` calls, lock inversions are physically impossible.

---

### Conclusion
The existing Semantic Graph and `SemanticWorkspace` are heavily equipped to handle cross-file mapping and thread-safe resolution. 

**The singular missing piece:**
We must formally add `Props []PropDecl` to the `Symbol` struct in `semantic_analyzer.go` so that the signature mathematically survives the journey from the AST into the Semantic Workspace.
