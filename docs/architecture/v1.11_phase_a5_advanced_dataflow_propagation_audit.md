# Phase A.5.2 — Advanced Data-Flow Propagation Audit

## 1. Architectural Mandate

The fundamental rule for Data-Flow Propagation in TinPyUI is the strict separation of concerns:

- **Data-Flow Engine (`dataflow_analyzer.go`)**: Determines *where* values come from (tracing the `FlowDependency` graph chronologically and topologically).
- **Type Engine (`type_engine.go`)**: Determines *what* those values mean. 

The Data-Flow Engine must **never** become a second Type Engine. It must solely resolve upstream dependencies, retrieve their established types, and pass them down to the Type Engine for mathematical or logical evaluation.

## 2. Dependency Traversal & Topological Ordering

Currently, the `DataFlowGraph` contains `DataFlowNode` entries connected by `FlowDependency` edges.
- **Traversal Strategy**: Since graph ordering cannot be assumed to be natively topological due to scattered declarations and out-of-order execution, the analyzer must traverse edges recursively (or via Kahn's algorithm) to compute types bottom-up.
- **Evaluation Order**: Before a node's type is inferred, all its `FlowDependency` upstream targets must be resolved. 

## 3. Chained Inference

Types must propagate losslessly through multi-hop derivations without premature truncation.
Example:
```tin
state count = 10
state total = count + 5
state average = total + 2.5
```
- `count` resolves natively to `Int`.
- `total` retrieves `count` (Int), passes `Int + Int` to `TypeEngine.InferExpression()`, yielding `Int`.
- `average` retrieves `total` (Int), passes `Int + Float` to `TypeEngine.InferExpression()`, yielding `Float`.

## 4. Multiple Dependencies

Expressions like `result = price + tax + discount` produce an n-ary tree in the AST (or chained binary operations).
- The `DataFlowAnalyzer` must resolve *every* unique identifier reference within the expression, retrieve their types, and evaluate the AST recursively using the Type Engine.
- If any node in the tree fails to resolve, propagation continues carefully handling the `Unknown` fallback.

## 5. Unknown vs. Any Propagation

A strict semantic distinction must be preserved during multi-hop propagation:
- **Unknown**: A value that *could not* be determined (e.g., missing import, syntax error, cycle).
  - If `A -> Unknown`, then `B = A + 10` must strictly evaluate to `Unknown` (`ConfidenceUnknown`). The compiler must *not* invent a type (like Int) simply because `+ 10` looks like an Int operation.
- **Any (`{dynamic}`)**: A legitimately untyped value provided by the host context.
  - If `A -> Any`, then `B = A + 10` must evaluate to `Any` (or `TypeConflict` depending on Type Engine strictness, but it must not be conflated with `Unknown`).

## 6. Cycle Termination

```tin
state A = B
state B = C
state C = A
```
Cycles in data-flow must terminate safely.
- **Cycle Guard**: The analyzer will maintain a `visiting` stack (or set) of node IDs.
- **Fallback**: If an edge points to a node already in the `visiting` set, the traversal must immediately halt for that branch and yield `TypeUnknown` (or emit a cycle diagnostic). It must *not* recurse indefinitely or crash the compiler.

## 7. Cross-File Dependencies

Data-Flow propagation across component or file boundaries must use the exact same `SemanticWorkspace` mechanisms established in Phase A.4.6.
- Resolving a dependency across files uses the `tinpy://...` semantic identity.
- No new file-resolution mechanics should be added to the Data-Flow analyzer. If `A` depends on `tinpy://fileB.tin#StateX`, it delegates to the workspace index.

## 8. Mutation and Data-Flow Interaction

When evaluating inline mutations like:
```tin
state count = 10
Update():
    count = count + 1
```
The analyzer must cleanly distinguish the state's *declared type* from the expression's *mutated type*.
- The analyzer retrieves `count`'s currently established global type (`Int`).
- It evaluates the RHS `count + 1` as `Int + Int -> Int`.
- It validates the assignment compatibility using `InferAssignment(Int, Int)`.
- If the mutation introduces an invalid type (e.g., `count = count + "string"`), it evaluates to `TypeMismatch` and does not taint the global state's original `Int` classification.

## 9. Branch Boundaries (Forward Looking)

A.5.2 establishes the linear expression flow. It will **not** prematurely implement full branch-aware environments (e.g., merging `if/else` types).
- **Preparation**: The analyzer will pass a simple scoped dictionary or context object (representing the `TypeEnvironment`) down the evaluation chain. 
- In A.5.2, this environment represents linear flow. In A.6/A.7, this object will be cloned/forked for branch traversal without breaking A.5.2's core architecture.

## 10. Performance & Memoization

Deep component trees and recursive state dependencies could lead to `O(N^2)` or exponential evaluation times if re-computed naively.
- **Memoization**: Once a `DataFlowNode` has been strictly typed (`TypeResult` computed), its result must be cached in the graph.
- Subsequent dependent requests for that node's type will return the cached `TypeResult` immediately, ensuring `O(N)` linear traversal scaling.

## Next Step
Upon approval of this design, **Phase A.5.2 Implementation** will translate these rules into `dataflow_analyzer.go`, strictly calling `type_engine.go` for all semantic decisions.
