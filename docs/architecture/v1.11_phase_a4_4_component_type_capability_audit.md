# TinPyUI v1.11 — Phase A.4.4: Component Type Capability Audit

This document answers core architectural questions regarding how component definitions, invocations, and properties are currently represented within the TinPyUI AST and Semantic Graph. The objective is to determine what data exists today and what is missing before implementing component property type-checking.

---

### 1. How does the AST distinguish a component invocation from other nodes?
In `src/compiler/ast.go`, an invocation is stored generically as a `*Node`. The AST itself does not explicitly flag a `Node` as a component invocation versus a standard UI tag.
However, the compiler implicitly distinguishes components based on capitalization conventions. In `src/compiler/semantic_analyzer.go`, it checks if the first letter of `Node.Name` is uppercase (`n.Name[0] >= 'A' && n.Name[0] <= 'Z'`) to determine if a node renders a custom component or a standard native element.

### 2. Where are positional arguments stored?
Invocations store positional arguments in `Node.Args []string`. This captures raw string values passed without named keys (e.g., passing `"Submit"` into `<Button>"Submit"</Button>`).

### 3. Where are named attributes stored?
Invocations store named properties in `Node.Attributes map[string]string`. This captures explicit key-value pairs (e.g., `disabled={loading}` maps to `"disabled": "{loading}"`).

### 4. How are component definitions represented?
A component is declared in the AST via the `Component` struct:
```go
type Component struct {
	Name      string
	Args      []string
	States    []*StateDecl
	Mutations []*DefNode
	RootNodes []ASTNode
	Range     Range
}
```
The Semantic Graph represents it as a `Symbol` with `Kind = SymbolComponent`.

### 5. Can a component define expected property types today?
**No.** The `Component.Args` field is just a `[]string` containing the names of the expected properties. There is absolutely no syntax or field in the AST for type signatures (e.g., no way to declare `disabled: Bool`).

### 6. Can component references be resolved through the existing Semantic Graph?
**Yes.** The `semantic_analyzer.go` already maps invocations to definitions using `RelRenders` edges. It effectively builds the target ID (using import maps for cross-file components, or local IDs for in-file definitions). Therefore, if we encounter `<Button>`, the Semantic Graph can successfully tell us exactly which `SymbolComponent` it points to.

### 7. What information is missing to safely type-check properties?
To safely assert that `Button(disabled=42)` is invalid, the compiler is missing **Component Signatures**. 
We need:
1. An extension to the `.tin` parser to allow type annotations on component arguments (e.g., `component Button(text: String, disabled: Bool)`).
2. An extension to `ast.Component` to track these types instead of just `Args []string`.
3. The Type Analyzer to map the inferred types of `Node.Attributes` against the newly defined Component Signatures.

### 8. Are component properties currently purely dynamic?
**Yes.** Because there are no type definitions, all property passing is currently accepted unconditionally by the compiler. Values are merely passed down as strings or expressions, and type mismatches (e.g., trying to execute math on a boolean) will only fail at runtime within the Python or Rust execution environments.

---

### Conclusion
The Semantic Graph correctly maps component relationships (`RelRenders`), meaning the structural plumbing is perfectly in place. However, the AST completely lacks property type signatures. 
Before we can implement `A.4.6 Component type checking`, we *must* execute `A.4.5 Component Type Model` to formalize how component signatures will be represented and stored.
