# v1.10 Phase 3: AST Extension Design

*Status: DRAFT / DESIGN PHASE*

This document defines the minimal, read-only architectural changes required to the Go compiler's AST (`src/compiler/types.go`) to capture the metadata needed by the TinPyUI Semantic Graph, without disrupting the existing execution IR (`generator.go`).

## 1. Architectural Strategy

The overarching goal is to modify the AST to retain source bounds and file boundaries so a new Semantic Graph builder can consume them. The existing execution pipeline will simply ignore these new fields.

**Pipeline View:**
```text
Parser.Parse() ──→ FileAST
                      ├── Imports (ignored by Generator)
                      ├── URI (ignored by Generator)
                      └── Components 
                             ├── Range (ignored by Generator)
                             └── Node tree ──→ Generator.Generate() ──→ IR
```

## 2. Minimum Struct Additions

To capture exact LSP-compliant source boundaries, we will introduce a standard `Range` struct.

```go
type Position struct {
	Line      int `json:"line"`
	Character int `json:"character"`
}

type Range struct {
	Start Position `json:"start"`
	End   Position `json:"end"`
}
```

## 3. Extending Existing AST Nodes

Every meaningful declaration must embed the `Range` struct to map back to the TinPyUI Semantic Graph.

```diff
  type Component struct {
  	Name      string
  	Args      []string
  	States    []*StateDecl
  	Mutations []*DefNode
  	RootNodes []ASTNode
+ 	Range     Range
  }

  type StateDecl struct {
  	Name    string
  	Initial string
+ 	Range   Range
  }

  type DefNode struct {
  	FuncName  string
  	Mutations []MutationNode
+ 	Range     Range
  }

  type Node struct {
  	Name       string
  	Args       []string
  	Attributes map[string]string
  	Children   []ASTNode
  	IsFString  bool
+ 	Range      Range
  }
```

## 4. Capturing the File Boundary (New Node)

Currently, `Parse()` returns `[]*Component`. This discards the file identity entirely. We must introduce a `FileAST` wrapper that natively supports the new `import` semantics necessary for cross-file dependency resolution.

```go
type ImportDecl struct {
	Path    string   // e.g. "ui/buttons.tin"
	Symbols []string // e.g. ["PrimaryButton", "DangerButton"]
	Range   Range
}

type FileAST struct {
	URI        string
	Imports    []*ImportDecl
	Components []*Component
}
```

## 5. Impact on Parser & Generator

**Parser Impact (`parser.go`)**:
- The parser will be updated to record `p.curToken.Line` and `p.curToken.Col` when it begins parsing a component/node, and record the closing token's location when finishing.
- A new `parseImport()` function will be added.
- `Parse()` will return `*FileAST` instead of `[]*Component`.

**Generator Impact (`generator.go`)**:
- `Generate()` currently accepts `[]*Component`. It will be trivially updated to accept `FileAST.Components`.
- It will completely ignore the `Range` property and `Imports` list, guaranteeing zero regressions in the frozen v1.9 runtime behavior.

## 6. Populating the Semantic Graph

Once these AST extensions are in place, a new file (`semantic_analyzer.go`) can be introduced. It will take the `FileAST`, walk the tree using the new `Range` data, and construct the `File` and `Symbol` objects exactly as defined in `v1.10_semantic_graph_schema.json`, applying the `tinpy://` namespace ID rules.
