# TinPyUI v1.11 — Type Inference & Data-Flow Architecture Specification

This document defines the formal architecture for the **v1.11 Semantic Intelligence Expansion**. The goal is to upgrade the existing TinPyUI semantic intelligence layer from structural awareness ("What exists and how things relate") to deep semantic meaning ("What things type as and how information moves").

By establishing strict Type Inference and Data-Flow (taint) analysis, AI agents acting through the Machine Protocol will possess deterministic insight into component safety, side-effects, and data propagation prior to proposing multi-file refactoring operations.

---

## 1. Architectural Boundaries

To prevent the core Semantic Graph from becoming an unmaintainable analysis monolith, the system enforces strict functional separation:

```text
┌─────────────────────────────────────────────────────────────┐
│ Semantic Graph (Current Foundation)                         │
│ Responsible for: "What exists and how things relate"        │
│ Defines nodes, structural linkage, parent-child relations,  │
│ and basic symbol references.                                │
└─────────────────────────────┬───────────────────────────────┘
                              │
         ┌────────────────────┴────────────────────┐
         ↓                                         ↓
┌─────────────────────┐                 ┌─────────────────────┐
│ Type Engine         │                 │ Data-Flow Engine    │
│ "What things mean"  │                 │ "How data moves"    │
│ Infers explicit and │                 │ Tracks assignments, │
│ implicit types.     │                 │ sources, and sinks. │
└────────┬────────────┘                 └──────────┬──────────┘
         │                                         │
         └────────────────────┬────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────┐
│ AI Context Layer (Machine Protocol)                         │
│ "How consumers query and act on analyses"                   │
│ Exposes context.types and context.dataflow. Ensures         │
│ AI remains a consumer, not the semantic authority.          │
└─────────────────────────────────────────────────────────────┘
```

> **CRITICAL ARCHITECTURAL RULE**  
> **Type inference may enrich semantic understanding, but it must never modify the canonical Semantic Graph or execution IR.**

The pipeline remains explicitly one-way to protect the v1.8.0 execution baseline:
```text
                    ┌── Type Engine ──────┐
AST → Semantic Graph                    ├→ AI / LSP
                    └── Data-Flow Engine ─┘

AST ─────────────────────────────────────→ Execution IR → WASM
```

## 2. Roadmap Phases

### Phase A: Type System Model (Refined)
The Type Engine operates strictly statically (no `.tin` code execution) over the AST and Semantic Graph to determine the canonical data types of variables, component properties, and expressions.

#### 1. Type Universe
The engine models types using the following exhaustive universe:
- `String`
- `Int`
- `Float`
- `Bool`
- `Null`
- `Unknown` (Explicitly unresolvable/missing type information)
- `Any` (Explicitly accepts all types, typically via API boundary)
- **Component / Reference Types**: Strongly typed references to declared `.tin` components (e.g., `<Button>`).
- **Collection Types**: Array/List representations (`[String]`, `[Int]`).

#### 2. Type Sources & Inference Hierarchy
Types are resolved in the following priority order, from strongest provenance to weakest:
1. **Explicit declaration**: Type hints or property signatures defined directly in source.
2. **Literal inference**: Deduced purely from constant initialization (e.g., `state message = "Hello"` → `String`).
3. **State inference**: Deduced from state lifecycle context and hook usage.
4. **Expression inference**: Deduced from mathematical or logical operations (e.g., `a + b` with operators inferring numeric/string return types).
5. **Component/API inference**: Derived from the documented return signature of external boundaries or standard library components.
6. **Unknown**: Fallback when all inference fails.

#### 3. Type Lattice
`Unknown` and `Any` are explicitly non-synonymous.
- `Any` is a known, valid Top Type that legally accepts all data.
- `Unknown` is an Uncertainty Marker representing a failure in the static inference boundary. 
- Validation layers must reject strict type checks against `Unknown` conservatively to avoid false negatives.

#### 4. Inference Confidence & Provenance
To allow AI consumers to weigh the validity of a type constraint, every computed type yields a structured result with provenance:
```text
TypeResult
 ├── type:       (e.g., Int)
 ├── source:     (e.g., LiteralInference)
 ├── confidence: (e.g., High, Medium, Low)
 └── range:      (TextRange identifying the AST node that provided the inference)
```

#### 5. Conflict Handling
TinPyUI handles type conflicts (e.g., `state value = 10; value = "hello"`) deterministically. 
If an assignment strictly violates an explicitly declared or highly confident statically inferred type, the engine evaluates the node as **`TypeConflict`** (a subclass of `Unknown` with attached diagnostic metadata). It does *not* dynamically cast `Int → String`.

#### 6. No Execution Semantics
The Type Engine is a purely static analytical tool. It traverses:
`AST → Semantic Graph → Type Engine`
It absolutely **does not** execute code (`AST → execute → observe → infer`).

#### 7. Data-Flow Identity Preparation
To ensure Phase B can safely overlay its directed graph, Phase A strictly defines the semantic identities it emits:
- **Definition**: The AST node initializing a symbol.
- **Assignment**: Subsequent structural writes to a symbol.
- **Read**: Terminal consumption nodes (e.g., UI rendering blocks).
- **Mutation**: In-place modifications (distinct from reassignment).
- **Parameter**: Component or function input boundaries.
- **Return**: Output boundaries.
- **Source**: Explicit taint origins (e.g., User Input, API responses).
- **Sink**: Explicit execution targets (e.g., Database calls, dangerous DOM evaluation).


### Phase B: Data-Flow Graph
The Data-Flow Engine overlays a directed flow-graph onto the structural Semantic Graph using the identities prepared in Phase A. 
- Tracks Propagation Rules (how data moves from variables → arguments → component props → DOM nodes).
- Maps all terminal read locations of a specific data definition.
- Exposes cross-component data flow mapping.

### Phase C: Analysis Engine
The runtime engine that orchestrates the execution of Phase A and B and makes them queryable.
- Exposes `context.types` and `context.dataflow`.
- Emits **Type Diagnostics** (e.g., passing `String` to `Bool` prop).
- Emits **Flow Diagnostics** (e.g., untyped data reaching an execution sink).
- Remains 100% deterministic, secured by VFS/docMutex locks.

### Phase D: AI Integration
Integrating the Intelligence Expansion directly into the Machine Protocol.
- Validation Consumption: `context.propose` validation rules automatically reject proposals introducing `TypeConflicts`.
- **AI as Consumer**: The Go backend asserts ultimate authority; the AI is never trusted as a semantic authority.

### Phase E: Safety Validation
- Unit test suites analyzing false-positives, false-negatives, and cycles.
- Validating Graceful Degradation for `Unknown` types and unresolved symbols.
- Performance boundary checks ensuring sub-50ms OODA loop for LSP operations.

### Phase F: Multi-File Refactoring Orchestrator
The final culmination of the v1.11 cycle. With Type and Data-Flow meanings established, TinPyUI can finally introduce the Multi-File Orchestrator, allowing AI agents to safely transaction-commit large architectural refactors.
